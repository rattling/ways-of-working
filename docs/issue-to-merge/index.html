The brief

A raw issue is usually one line. Before it builds anything, /ways:work rewrites it as a brief on the issue and waits for you to say go. The brief is finished when Claude could start from the issue alone, without the conversation that produced it.

The working contract

Who decides

Most wasted turns are one of two mistakes: Claude asking permission for something it owns, or quietly deciding something it doesn't. Click each item to give it to a person or to Claude, then check.

What escalating looks like

In rehearsal, three tickets into an autonomous build of the recipes milestone, the run stopped to ask a domain question. The supplier left allergens blank on plain produce, and we'd agreed blank means not declared, not none. So a squeeze of lemon left every dish "allergens not confirmed", and the spec's own check couldn't pass.

It didn't pick quietly. It set out the conflict, recommended an answer, and kept building the next ticket while it waited. That's the rule: state the decision, give a recommendation, and carry on with everything that doesn't depend on it.

Review and merge

Merging by risk

Risk is set by what a change touches, not by who wrote it. The engineering lead sets a dial per repo and moves it as trust builds. Choose the files a PR changes and where the dial sits.

The dial, in AGENTS.md

Tier
    Three layers, every PR
    1. Before the PR. The gate is green (your tests, lint and checks, as one command) and Pocock's code-review has run in fresh-context subagents. Every finding gets an answer: fixed, or not a problem because.
    2. On the PR. CI runs the same gate. It's the required check.
    3. People. Approval scaled to risk, as on the left. An agent's approval never counts as a person's.

    The agent can raise a tier, never lower it. High is enforced by CODEOWNERS and a branch rule, not by the agent's judgement. While a team is new to the method, keep the dial on learning.

    The band and the context window

    When to clear

    A big context costs usage on every message, because the whole conversation is sent again, and it thins Claude's attention. Compaction loses detail. Everything that matters lives in files and GitHub, so a fresh session picks up from there. The band above the prompt shows where you are. Move the slider and pick what you're doing.

    One session per piece of work. Start each build in a fresh session, and don't chat in the build's session. If you want to explore while a build runs, open a second session: the desktop app gives it its own worktree.

    A model per ticket

    When /ways:build cuts tickets, it picks the cheapest model that will get each one right, and says why in one line. Nobody has to choose, and you can disagree. Which would it pick?

    Measured, once each

    A method can oversteer

    The same request, a printable allergen chart for each café's wall that says when the printed copy is out of date, on the same app, three ways. A version of ways that accepted every recommended extra built six times the code. The fix was proportion: the plan states the expected size against the nearest existing feature, the grill leans small, and extras go on a Later list.

    One run each, so indicative. Times are build time, not planning. Pocock's chain on its own wasn't tested.

    Prompt injection

    The agent reads things you didn't write

    Issues, bug reports, review comments, a supplier's CSV, a dependency's README, a web page. Any of them can carry text that tries to give Claude orders. Simon Willison calls the risk the lethal trifecta. Switch on what a coding agent with your permissions has.

    Each on its own is fine.

    Layers, not one wall

    • Permissions: .env denied in the repo's settings
    • Auto mode stops risky actions and asks
    • Hooks, which run whatever the agent thinks
    • Review: the diff is the boundary
    • The admin's managed settings, for the whole organisation

    Preparing a workshop, auto mode stopped Claude from force-pushing a repo, and from commenting on another project's issue without asking.

    Habits

    • No live secrets where the agent runs
    • Read permission prompts before you approve them
    • Trusted plugins and MCP servers only
    • Read the diff, especially config, CI and dependencies
    • Treat instructions inside content as a red flag, and say so
    On the desk

    The four commands

    A person types each one. Claude never starts the next step itself. Each command checks what's already done, so running it twice never repeats work, opens by saying where you are, and ends by naming the one PR to merge and the next command.

    /ways:discover

    The ask is a wish list or a half-built app. Ends in a one-page brief and an issue to plan from.

    /ways:plan #n

    Big work. Requirements then design, in one sitting. Ends in one spec PR.

    /ways:build #n

    The spec is merged. Tickets, code on one integration branch, a review. Ends in one PR that ships it.

    /ways:work #n

    Small work. Sizes, reproduces and briefs a raw issue, waits for go. Ends in one reviewed PR.

    Also: /triage for a queue of new issues, /ways:mock for anything people look at, /ways:explain before working in code you don't know, /ways:arch-review every so often, /ways:setup to set a repo up or bring it up to date.
