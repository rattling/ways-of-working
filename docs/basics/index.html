A field guide for people building with AI

Software engineering, in one page

You can get a long way building with Claude without any of this. Then something breaks, or a second person needs to use it, or a customer's data goes somewhere it shouldn't. Software engineering is mostly about what happens after the first version works.

This page won't teach it all: that's a long course. It's a map of the ground, eight stops, so you know what's out there, roughly how it fits together, and when each piece will start to matter. Each stop has a drawing, the idea in plain words, and where to go next. Tick off the ones you're comfortable with.

Stop 1

The problem, before the code

Bites: before you start

Most software fails because it solves the wrong problem, not because the code is bad. An idea usually arrives as a solution ("we need a dashboard"). Work back to the problem: who has it, what it costs them, and what you'd see if it went away. Then build the smallest thing that tests whether you're right. Often the first answer is a change to how people work, and needs no code at all.

You'll hit this when

You've built something nobody uses, or three people want three different things from it.

Go further
  • The Mom Test, Rob Fitzpatrick: how to ask people about problems without them lying to you
Stop 2

How an app is put together

Bites: before you start

Most apps have three parts. The front end is the screens, running in the user's browser. The back end is code on a server that holds the rules and decides what's allowed. The database keeps the data. They're separate on purpose: anything in the browser can be read and changed by the user, so the rules and the data live behind the back end.

It also helps to keep design time and runtime apart in your head. Claude helps you write the code at design time. At runtime, the app runs on its own for your users, and Claude isn't there. If your app needs AI while people use it, that's a separate part you build in on purpose.

You'll hit this when

A rule only exists in the screen, and someone gets round it. Or you can't tell why something works on your laptop and not on the server.

Go further
  • MDN's learning area: how the web works, from the people who document it
  • The Missing Semester, MIT: the tools nobody teaches
Stop 3

Data

Bites: before you start

A database is mostly tables: rows and columns, like a spreadsheet with rules. The big idea is that each fact lives in one place. Aoife's email is stored once, and her orders point at her. Copy it into every order and one day the copies disagree, and nobody knows which is right.

Two other things to know early. Data about people is personal data, and the law cares where it goes, including into an AI tool. And analysing data (questions about last month) is a different job from running the app on it. Don't point a report at the live database without thinking about it.

You'll hit this when

Two screens show different answers for the same thing, or you need to change how something is stored and everything breaks.

Go further
  • SQLBolt: SQL, the language of databases, in short interactive lessons
  • The PostgreSQL tutorial
Stop 4

Talking to other systems: APIs, and MCP

Bites: when you connect things

An API is how one program asks another to do something: a request goes out, a response comes back. Your front end talks to your back end through one. Your app talks to a payment provider through theirs. An API is a promise to whoever uses it, so once something depends on it, change it carefully: add to it, don't break it.

MCP is the same idea for AI agents: a standard way to give an agent tools, like "look up a customer" or "log time". It usually sits in front of your existing API, so the agent goes through the same rules a person does.

You'll hit this when

You connect to a service like payments or email, or you want Claude to use your app directly.

Go further
  • An overview of HTTP, MDN: what a request and response really are
  • modelcontextprotocol.io: MCP's own introduction
Stop 5

Who can use it

Bites: before anyone else uses it

Two different questions, often mixed up. Authentication is who you are: signing in. Authorisation is what you're allowed to do once you're in: a manager can see everyone's hours, a staff member only their own. Both are checked in the back end, every time, never just by hiding a button on the screen.

Don't build sign-in yourself: use a proven service (Google, Microsoft, or a library made for it). And keep secrets, like passwords, API keys and database logins, out of your code and out of anything you paste into a chat. They go in settings on the server.

You'll hit this when

A second person signs in, a customer sees someone else's data, or a key ends up on GitHub.

Go further
  • OWASP's authentication cheat sheet: what the security people check
Stop 6

Where it runs

Bites: before anyone else uses it

Your app runs somewhere: a server, or a cloud service that manages servers for you. Deploying is getting a new version there. Do it the same way every time, by a script or a pipeline, never by hand, and make sure you can go back to the last version if the new one breaks.

Keep separate environments: your laptop to try things, a test copy with made-up data, and production with real users. And describe the servers themselves in files (infrastructure as code), so test and production are built the same way, you can rebuild either, and Claude can read and change them like any other code.

You'll hit this when

It works on your laptop but not live, you're scared to deploy, or nobody remembers how the server was set up.

Go further
  • The Twelve-Factor App: short rules for apps that deploy cleanly
  • Azure's Well-Architected Framework: the questions to ask of anything you host
Stop 7

Keeping track, and working together

Bites: before you start

Git keeps every version of your code, so you can see what changed, when, and why, and undo it. The trusted version lives on a line called main. Each change goes on its own short branch, and comes back through a pull request: a page that shows exactly what changed, where someone (or a check) reviews it before it's merged.

Keep branches short and changes small. A small change is easy to review and easy to undo; a week's worth is neither. GitHub is where most teams keep the repo and the pull requests.

You'll hit this when

Something worked yesterday and doesn't today, or two people change the same thing at once.

Go further

  • Pro Git: the free book, when you want the detail
Stop 8

The engineer's habits

Bites: from the first day

Engineers have a habit of asking "how could this fail, and how would I know?" before they ship. That's most of the mindset. It shows up as tests: small programs that check your code still does what it should, run every time anything changes, so a fix here doesn't quietly break something there. Claude writes them well, if you ask it to and check they test the right thing.

The rest is small steps and leaving things tidy. Change one thing at a time, so when something breaks you know what did it. Write down the decisions that would surprise the next person, which is often you, or Claude in a new session. And watch the app once it's live, so you hear about problems before your users tell you.

You'll hit this when

Fixing one bug creates two more, or you're afraid to touch a part of the app.

Go further
  • The Practical Test Pyramid, Ham Vocke on Martin Fowler's site: what kinds of tests to write

You don't have to know all of this to start

You need to know it's there. Build with Claude, and when one of these stops starts to bite, come back to it. Better still, work in a way that has the guardrails built in, so the checks happen whether or not you remember them.
